# ⑧ CMS 構築・運用マニュアル

CMS：**Decap CMS**（Git ベース。原稿は `site/src/content/` のファイルとして保存され、保存のたびにサイトが自動で再ビルドされる）
管理画面：`https://（本番ドメイン）/admin/`　設定：`site/public/admin/config.yml`

## 1. 誰が・何を更新するか

| CMS のメニュー | 中身 | 想定する更新者・頻度 |
|---|---|---|
| ニュース | お知らせ・店舗・採用・地域 | クライアント担当者／随時 |
| 社員インタビュー | PEOPLE と採用サイトで共通 | 制作会社（取材後）／年2〜4本 |
| 募集要項 | 新卒・中途の職種と要項。「募集中」のオン／オフ | 採用担当／募集のたび |
| 03 事業 | 4事業の「4つの問い」・写真・担当者の言葉 | 制作会社／原稿確定時 |
| 章（01〜05） | 章名・問い・TOP の予告文・章扉の写真 | 制作会社のみ（順番・URL は変えない） |
| ページ原稿 | TOP / 01 理念 / 02 フィロソフィ / 03 事業 / 04 人 / 05 地域 / 採用サイト | 制作会社／原稿確定時 |
| 会社データ | 会社情報・拠点（店舗）・沿革・お問い合わせ窓口・プライバシーポリシー | クライアント担当者／変更時 |

## 2. 原稿の入れ方（制作中のルール）

1. **【…】は仮置き**。正式原稿に置き換えると、サイト上の青い破線表示が自然に消える。原稿がない箇所は創作しない
2. **「クライアント確認済み」スイッチ**：会社データ・沿革・数字などは、確認が取れたものからオンにする。オフの間はサイトに「要確認」バッジが出る
3. **写真**：各写真枠の「画像」に画像をアップロードし、「代替テキスト」に写真の説明を書く。撮影指示・撮影リストNo は撮影が済めば消してよい（docs/05_photo_list.md と対応）
4. **フィロソフィ**：正式原稿の項目数に合わせて項目を増減する（番号 02-1… は自動で振られる）。原稿が入ったら「整理枠」は空にする
5. **沿革**：会社情報には全件、01 理念「1963年からの歩み」には「歩みに表示」をオンにしたものだけが出る（転機を5〜7つに絞る）
6. **事業の独立ページ化**：原稿量が増えたら「独立ページにする」をオン → `/business/{URL用の名前}/` が生成され、各所のリンクも切り替わる
7. 残数の確認：制作側で `npm run check:placeholders` を実行すると、仮置き・要確認の残りがファイル別に一覧できる

## 3. 公開の流れ（承認フロー）

`publish_mode: editorial_workflow` を有効にしている。

```
編集 → [下書き] → [レビュー待ち] → [公開準備完了] → 公開
                       ↑ 制作会社 or 社内責任者が確認
```

- 管理画面の「ワークフロー」タブで、公開待ちの原稿をカンバン形式で確認できる
- GitHub 上では各原稿がプルリクエストとして作られ、公開＝マージ。マージ後に自動で再ビルドされ、数分で本番に反映される
- 急ぎのお知らせなど承認不要な運用にする場合は `config.yml` の `publish_mode` 行を削除する

## 4. ログイン（バックエンド）の設定

Decap CMS は GitHub アカウントでログインし、リポジトリに直接コミットする。

| ホスティング | 設定 |
|---|---|
| Netlify | Netlify の管理画面で GitHub OAuth を設定（Site configuration → Access control → OAuth → GitHub）。`config.yml` はそのまま |
| Cloudflare Pages / Vercel など | GitHub OAuth App を作成し、OAuth プロキシ（例：decap-proxy を Cloudflare Workers に配置）を用意して `config.yml` の `backend.base_url` に URL を設定 |

- `backend.repo` / `backend.branch` は本番運用するリポジトリ・ブランチに合わせて変更する
- 編集者には GitHub アカウントを作成してもらい、リポジトリへの書き込み権限を付与する
- GitHub アカウントを持たない担当者が多い場合は、Netlify Identity 等の代替やヘッドレス CMS（microCMS など）への切り替えを検討する。コンテンツモデル（`site/src/content.config.ts`）は CMS に依存しない形で定義してあるので、データ取得部分（`site/src/lib/data.ts`）の差し替えで移行できる

## 5. ローカルでの編集（制作者向け）

GitHub ログインなしで、手元のファイルを直接編集できる。

```bash
cd site
npm run cms    # CMS 用ローカルサーバー（ポート 8081）
npm run dev    # 別ターミナルで開発サーバー
# → http://localhost:4321/admin/index.html を開き「ログイン」を押す
```

保存するとすぐに `site/src/content/` のファイルが書き換わり、開発サーバーのページにも反映される。

## 6. 入力項目を増やすとき（制作者向け）

入力項目は **2か所を必ずセットで** 変更する。

1. `site/src/content.config.ts` … データの型（サイト側がビルド時に検証する）
2. `site/public/admin/config.yml` … CMS の入力画面

片方だけ変えると、CMS で保存した原稿がビルドエラーになる（エラーメッセージにファイル名と項目名が出る）。テンプレート（`site/src/pages/`）で新しい項目を表示して完了。

## 7. トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| 保存したのに反映されない | ワークフローで「公開」まで進んでいるか確認。公開済みならホスティングのビルドログを確認 |
| ビルドが失敗した | ログの `InvalidContentEntryDataError` に出るファイル・項目を CMS で修正（必須項目の空欄が多い） |
| 画像が大きく表示が重い | アップロード前に長辺 2400px・JPEG 品質 80 程度に縮小する |
| 「要確認」が消えない | その項目の「クライアント確認済み」をオンにする |
